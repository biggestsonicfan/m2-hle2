# Savestates (`core/savestate.h`, board-level)

Part of m2-hle2's load-bearing invariants, indexed in [CLAUDE.md](../../CLAUDE.md): facts reverse-engineered or debugged into the emulator, in no datasheet. Do not re-derive them.

A savestate is a zip, as m2emulator's `.sta` is: one raw entry per board component (`I960`, `SHARC`, `COP`, each bus buffer under its region name, `GEO`, `GEOHELD`, `IRQT`, `M68K`, `M2SCSP`, `SOUND`, `EMU`, `HLE`, a profile's `P.<name>`), plus `INFO`, `LAYOUT` and `ROM`. `save_state` / `load_state` over the bridge, `--load-state FILE` at launch, `det_digest --save-at F:FILE` / `--load FILE`.

- **It is exact, and that is what to hold it to:** `det_digest` saved at frame 400 and loaded in a fresh process gives the same rows and sample hash from there on, the 68000 and `--sound-hle` alike; two processes that load the same file and run 300 frames save identical entries.
- **A load is refused unless the file's `ROM` and `LAYOUT` match** (FNV-64 of every ROM; every struct's size). The structs are written raw, so a build that changes one cannot read an old file, and must not try.
- **Host pointers are written as NULL and kept live on load**: `g_cop.ctl`, `sharc_dm_ext`, the SCSP's RAM, clock and sink. The SCSP's LFO table pointers go in as ids. A new pointer field in a saved struct needs the same, or the file differs between processes and the load writes a stale address.
- **State outside the structs has to be registered.** A profile's own statics (`sfight_console`'s hidden-select latch) go through `savestate_extra` from its install; the run loop's latches are in `EMU`, the hooks' in `HLE`. A static that `grade-reset.mjs` needs cleared almost certainly needs saving too.
- **The geometrizer's held mode, LOD and z-adjust travel too** (`GEOHELD`, `g_geo_held` in `memory.h`; rollback `GEO.held`). GEO commands 07/17, 16 and 08/18 hold from one list to the next, and hotd sends its mode 2 and LOD 4 only in its first lists. They used to live in the renderer alone, so a state loaded before the board had sent them drew with mode 0 and LOD 0, and the mansion doors came out black and the zombies white (Pinboard #1045). The emu thread follows them as each list is applied, each published list carries the values it starts with, and the renderer starts its walk from those. A state from before this entry loads without it and keeps what the process had. A GGPO cold boot (`geodl_snaps_clear`) zeroes them, since the game sends them again as it boots.
- **The battery travels with the state** (`M2BACK`): a load puts the board's SRAM back as it was at the save, as MAME's does.
- **No load inside a netplay session or SKY EYE**: one board of two, or a camera record the game did not write.
- **The libretro core saves rollback.h's flat state, not the zip** (`rollback_flat_save`, `emu_state_flat_save`; Pinboard #585). Rewind saves a state every frame, and the zip took ~40 ms; the flat copy takes 3-6 ms and loads in 3-5. It is GGPO's snapshot behind a header (magic `M2LR`, version, `LAYOUT`, the `ROM` ids, the profile, an FNV of the part names and sizes), with the host pointers of the parts flagged `ptrs` (SHARC, COP, M2SCSP) packed as a savestate packs them, so a file from another process still loads; the load keeps the live ones. A load takes the flat state or an old zip. `retro_serialize_size` measures it once per load and adds 4096 bytes, and the save zero-pads the rest, because RetroArch asks the size once and rewind and run-ahead expect it to stay put. A state is about 6.7 MB, which is why RetroArch's own netplay still cannot run the core (it sends states). The `.info` has to say `savestate = "true"` (RetroArch refuses a save outright on `false`, before it ever asks the core) and `savestate_features = "serialized"` for rewind.
  - **RetroArch never re-reads a cached core's `.info`** (`core_info.cache`, keyed by file name only), so a player who had the core from before #585 kept "basic": no Frame Throttle > Rewind, and the hotkey refused (Pinboard #587). `lr_check_info_cache` reads the cache at load (`core/ra_info_cache.h`: rzip, then the entry's `savestate_support_level`), and below SERIALIZED leaves `core_info.refresh` beside it, the marker that makes RetroArch rebuild it. RetroArch 1.18 inits its core info again after the load, so Rewind and the hotkey work in that same session (measured on Xvfb against a stale cache); the notice still says to restart if not. `det_digest --rewind K` (K ≤ 60: K + 1 states are kept) goes back K frames every K and runs them again; its rows and sound hash must equal a plain run's (`--no-sound-thread` for the hash).
- **Every byte of the state is paid for every frame while rewind is on** (Pinboard #590). RetroArch serializes the whole state each frame and then compares it word for word with the last one (`state_manager_raw_compress`), so the cost is the state's size, not what changed: at 16 MB that was ~64 MB of memory traffic a frame, and the ARC-S overheated and stuttered. Only ~70 4 KB pages change in a frame. Four things were dead weight and went: 7 MB of RAM at 0x01100000-0x017FFFFF that no game touched (MAME mirrors the tile block at 0x01100000 and maps nothing above it; FV's boot writes zeros at 0x01419000, which MAME drops too), the 1 MB COP write-stream ring (a bridge debugging record, now `g_cop_capture` outside `g_cop`), a 512 KB framebuffer at 0x12C00000 that MAME does not have, and RAM2 past MAME's 256 KB. `det_digest --cpu --sound` was identical over 8000 frames of STF and 5000 of FV; a save went from 3.8 ms to 1.2 ms on x86. Keep large host-only buffers out of the parts `savestate.h` lists.
  - **A save copies the board before it waits for the sound thread** (`rollback_save_to`, Pinboard #594). The sound run writes only `g_sound` and `g_shle`, so every other part is copied while it runs, then `sound_settle()`, then the sound parts and META (`rollback_part_t.late`). Waiting first serialized the whole sound frame (~3 ms on the A55) onto every rewind frame. The flat pack writes the host-pointer ids into the destination in place, never through a temporary copy of the part. `det_digest --rewind K --rewind-census` prints, per part, the 64-byte lines that change a frame: about 450, spread over nearly every part, so a hot/cold split of the state buys nothing.
- **Fast-forward is RetroArch's: the core never paces itself, so it already runs as fast as the host goes.** While `RETRO_ENVIRONMENT_GET_FASTFORWARDING` says so, `lr_draw_every` draws one board frame in four (`LR_FF_DRAW_EVERY`) and dupes the rest, since the draw is what holds it back.
