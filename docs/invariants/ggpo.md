# Rollback netplay: GGPO (`core/emu_ggpo.h`, `core/rollback.h`, `net/ggpo_lobby.h`, Pinboard #575)

Part of m2-hle2's load-bearing invariants, indexed in [CLAUDE.md](../../CLAUDE.md): facts reverse-engineered or debugged into the emulator, in no datasheet. Do not re-derive them.

The second way to play online, beside RPCN lockstep: [GGPO](https://github.com/pond3r/ggpo) (MIT, `vendor/ggpo`, built by `cmake/ggpo.cmake`) runs a frame at once on a guess of the peer's input and, when the real input differs, loads the last frame both agreed on and runs forward again. Every frontend has it (`M2HLE_GGPO`, and only when `vendor/ggpo` is checked out; the canary and Pages builds fetch it): the desktop's command line and bridge, the web page's GGPO panel (`web/site/m2hle-ggpo.js` over `web_ggpo_post` / `web_ggpo_status`; `?ggpo=ws://...` names another lobby), and the libretro core's Online play "GGPO", set up in `<saves>/m2hle-ggpo.cfg` (keys `url`, `user`, `pass`, `challenge`, `accept`, `ws`, `synclog`).

- **A session is a cold boot on both machines, as an RPCN session is** (`emu_ggpo_cold_boot`: the battery detached, `g_hle_extra_session_off`, netplay's reset). One GGPO frame is one board frame (a slice to the vblank), and each player's input is netplay's canonical word.
- **A rollback snapshot is the savestate's parts copied raw** (`rollback.h`, ~16 MB, pooled: GGPO keeps about ten). No zip and no pointer packing: a snapshot never leaves the process, so its host pointers are still the live ones. What a savestate load does around the copy (the GEO's published state, the bus's generations, the sound board's page map) a rollback does too, through the same savestate.h helpers. A new part of the board goes in `savestate.h` and is then in both.
- **The checksum masks the host pointers** (`rollback__pack_*`: the SHARC's bufferram link, the COP's `ctl`, the SCSP's RAM and LFO pointers), as `savestate_save` does. Without it two processes' checksums never agree, and GGPO's desync check and the logged check lines are noise.
- **Frames run again are muted** (`g_sound_mute`, `sound.h`): the host heard them the first time. The sound board's clock still moves, so the UART and everything the i960 reads are unchanged.
- **Proving it:** `--ggpo-synctest N` rolls every frame back N frames and checks the snapshot's checksum against the first run (`--ggpo-synclog DIR` writes both sides part by part on a mismatch). In a session each side logs `ggpo: frame N board XXXXXXXX` every 600 frames, and the two logs have to be identical; `--ggpo-delay 0` makes a local pair roll back constantly.
- **The input delay is picked once, from the first ping** (`--ggpo-delay auto`, the default; Pinboard #1258). A fixed 2 frames made a far peer roll back 6-8 frames, and VF2 replays a frame at about the cost of a live one (~3 ms here), so each late input cost a 20-35 ms host frame: dropped frames, and stalls at GGPO's 8-frame prediction limit. `emu_ggpo__delay_ready` holds the local input until GGPO's first quality report gives a ping (up to 360 frames: the first reports are often lost while the peer still synchronizes), then sets one-way frames + 1 - 3 (rollbacks of about 3 frames), clamped to 2..7. GGPO's `_round_trip_time` is uninitialised until its first quality reply, so the ping read at RUNNING (`g_ggpo.ping_unset`) does not count: one live match read 616435125 ms there and set 7 frames (Pinboard #1268). **Never change it mid-session**: `InputQueue::AdvanceQueueHead` pads the new frames locally only, which leaves a hole in the input stream the peer is sent. The delay is local; the two sides may differ. Timesync's holds (`g_ggpo.skip`) are spread one per `EMU_GGPO_HOLD_GAP` (4) frames, not taken in a row. Every 600 frames P2P logs `ggpo: net frame N: ping, delay, direct/relayed; rollbacks, frames again, holds, stalls`: a player's log tells a relayed match (300+ ms through the droplet) from a far one.
- **The lobby is ggpo-server** (`ggpo.sonicthefighte.rs`, its own repository): JSON over a WebSocket (`/ws`) for accounts, a channel per game (the profile's id) and challenges; then UDP on one socket of ours: HELLO to the server until it answers PEER, punches to the peer, RELAY through the server until a punch says the peer hears us. GGPO is told its peer is `169.254.0.1:1` and gets the lobby's transport (`ggpo_port_set_transport`), which reports every peer packet, direct or relayed, as coming from there. So a match starts on the relay and moves to the direct path without GGPO noticing. **Two players behind one public IP punch each other's LAN address** (Pinboard #1258): most routers don't loop a packet back to their own public address, so such a pair used to relay through the US droplet, 300+ ms apart in one city. HELLO carries our LAN address (`net_local_ipv4_towards` the server, the socket's port); the server passes it as LOCAL (6) only to a peer at the same public IP, and the first LAN address the peer answers from becomes the peer's. Needs ggpo-server from the local-candidates change on; either side old is the old behaviour. **A punch names the match, and is punched to the GGL_GUESS (32) ports above the peer's address until the peer is heard** (Pinboard #1268): a NAT that maps each destination to a new port ("symmetric"; a home router here gave the server's port + 2..4) shows the peer another port than the server saw, so the punches died at both ends and the pair relayed. The guesses open our NAT to the peer's new port, and a punch carrying our match id becomes the peer's address wherever it comes from (`ggl__punch_ours`). The NAT hands out ports in order but jumps to a new block every few seconds, so **the match's UDP waits until the GGPO session is open** (`ggl__match_tick`): HELLO used to go before the ~5 s board reload that opens it, and the first punch left that much later from a port out of the peer's guesses. `the peer is at ..., N ms after our first hello` logs that wait. Checked through iVPN Tokyo against a home connection on the live lobby: 8 of 10 matches direct, both misses before HELLO waited (3 of 3 since); the old client relayed. An old peer's punch has no match id; it still counts only from the PEER address.
- **A browser has no UDP, so its match rides the lobby's WebSocket** (`via_ws`): the same `GGPO` datagrams go up as binary messages, the server answers SEEN as `ws` port 0, sends no PEER, and relays the whole match, also to a native peer on UDP. `--ggpo-ws` (cfg `ws=1`) makes a native client do the same, to test it. Needs ggpo-server from `cc73062` on.
- **Two things a cold boot leaves behind on purpose, which the checksum has to ignore or clear.** The host sample clocks (`g_sound.out_total`, `g_frame_clock.sample`) survive a board reset so an A/V client hears no seam; `rollback__pack_meta` zeroes them in the hashed copy. The published display-list snapshots (`g_geodl_snaps`) held whatever the last frames before the boot drew; `emu_ggpo_cold_boot` clears them (`geodl_snaps_clear`). Either one made two machines' checks differ from the first, with the boards identical.
- **A load's frame number comes from its buffer's address** (`g_ggpo.saved`, read by `emu_ggpo_cb_load` for the result count and the replay's rewind). GGPO frees a snapshot about ten frames later and the pool hands the same address to a new one, so `emu_ggpo_cb_free` forgets it; before that fix a load often read the frame from ten frames earlier, and a result seen just before a rollback was never counted (Pinboard #584).
- **The GGPO library's C++ files see `web_socket.h` through `net_socket.h`**, and an `EM_JS` defines its function in every file that includes it: under C++ the header only declares them, and main_web.c (C) defines them.
- **A linked game's match is both cabinets on each machine** (`core/emu_twin.h`, a profile's `link_twin`, Pinboard #1080; Virtual-On, Power Sled #1095). GGPO rolls back one process's board, and a comm link is two boards, so each machine runs both: board A the MASTER (player 1's), board B the SLAVE (player 2's), swapped through the one set of globals every frame. The live board is the local player's (drawn, heard), the other runs muted. A snapshot is `[A][B][link]`, where the link is the per-direction message queues (`emu_twin_link_t`): each board's sends of frame N reach the other in frame N+1, whichever board ran first, so the order of the two runs never shows. The input word is player 1's lever set in bits 0..9 and player 2's in 12..21 (Virtual-On's two levers are one cabinet's P1 and P2 sets).
- **The roles come from the cold boot, as an RPCN room's do** (`comm_role.h`): the board boots alone (muted) until `link_role(MASTER)` takes (vonj: frame 285), its backup block is A's; `link_role(SLAVE)` gives B's; each board then boots with its block and the twin peer. `m2comm_linked()` is false for a twin peer (`peer->twin`): there is no host link to pace (`link_pace.h`) and nothing stops a state load.
- **Four board copies a frame** (run L, save, load H, run H, save, load L): `rollback.diff` makes the twin's copies 4 KB compares that write only what differs (same bytes; most of a board is the same in both cabinets and a few frames apart). With it a pair on this container: ~12 ms of work a frame, 60 Hz; without, ~16 ms and 54 fps. The desktop UI thread draws under the emu mutex while a twin runs (`g_twin.ui_lock`): the hidden board passes through the bus.
- **SOLO is a twin with no GGPO** (`EMU_GGPO_SOLO`, a profile's `link_solo`, Pinboard #1110; Power Sled). A linked game loaded alone, outside a room, a GGPO match, a replay or a follow, runs its other cabinet beside the player's, and `link_solo` drives that board's keys each frame from its own RAM (Power Sled's operator: Call, Step twice, Go off race state 0x53E744). Nothing is saved for anyone, so the hidden board stays in `g_twin.stash` and swaps with the live one in place (`rollback__swap`): two passes a frame, not four (Power Sled native ~9 ms of work a frame, was ~14). `emu_ggpo_active()` and `emu_ggpo_match()` are false in SOLO: pause, reset and the shell treat the player as alone; a match, a room or `--comm-master/--comm-slave` stops SOLO first (`emu_ggpo_tick`), and `--ggpo-solo 0` keeps it off. Local only: no `NETPLAY_PROTO_REV` bump.
- **Power Sled is the Main unit (player 1, board A) against one ride (player 2, board B)**: a real race is three boards (the Main and two rides), and only two fit a GGPO match, so player 1 runs the Main's panel (call, step, start) and player 2 races. Its unit is ROM bytes (`powsled_set_unit`), not backup RAM, so `link_role` is set before each board's reset and the bytes go with the board as savestate extras (`UNIT.*`). **Not Daytona** (its comm board is a link of one; no `link_role`). GGPO has no protocol rev: an old build against a new one on a linked game plays one board against two and splits at once, which the check lines show. `node tools/von-ggpo-pair.mjs --exe <m2hle> --rom $ROMS_DIR/vonj.zip` plays a pair over 127.0.0.1 to a versus round (roles, link_ID, net_flag, VersusMode, 60 Hz, the check lines); `node tools/powsled-ggpo-pair.mjs --exe <m2hle> --rom $ROMS_DIR/powsled.zip --lobby ws://127.0.0.1:<port>/ws [--relay]` matches two through a local ggpo-server and races (race state 7 on both, link up, 60 Hz, the check lines); `--ggpo-synctest 1` rolls both boards back every frame. **Motor Raid** (#1627) is the plain case: board A the MASTER, board B the SLAVE, each a rider; its role and CABINET ID are hooks on `_InitGameSet` (`g_motoraid_link`, a savestate extra `LINK`), and `node tools/motoraid-ggpo-pair.mjs` races through a local ggpo-server (no NETWORK ERROR, race clock running, link up, 60 Hz, the check lines).
- **Test against a local ggpo-server only** (`GGPO_PUBLIC_HOST=127.0.0.1`, free ports), never the live one. Two headless clients: `--ggpo-lobby ws://127.0.0.1:PORT/ws --ggpo-signup --ggpo-user A --ggpo-pass PW --ggpo-challenge B` and the same with `--ggpo-user B --ggpo-accept any`; `--ggpo-relay` keeps a side off the direct path. Over the bridge, `{"cmd":"ggpo_lobby"}` reports the lobby and `"do"` drives it (connect, login, signup, join, challenge, accept, ...). Without a lobby, `--ggpo-remote IP:PORT --ggpo-player 1|2 --ggpo-local PORT` plays straight to an address. The web panel's check is two headless Chromes (or one and a native client) on `tools/web-serve.mjs` with `?rom=/dev-rom.zip&ggpo=ws://127.0.0.1:PORT/ws`: the `ggpo: frame N board` lines come out on the console.
