# Memory Bus (board-level)

Part of m2-hle2's load-bearing invariants, indexed in [CLAUDE.md](../../CLAUDE.md): facts reverse-engineered or debugged into the emulator, in no datasheet. Do not re-derive them.

- **Region table is linear-scanned in declaration order.** TILE (`0x01000000`) MUST appear before H_SYNC (`0x01040000`) or H_SYNC reads route to the TILE handler.
- **IO region initializes to `0xFF`, not `0x00`** (hardware idle state).
- **Tile RAM is 64K and mirrors at `0x01010000`** (MAME `mirror(0x110000)`); the `TILE_MIRROR` region shares TILE's buffer and must precede TILE in the table.
  - *Symptom that surfaced this in STF:* the NEXT MATCH screen had no KNUCKLES nameplate. `rm_char_disp_int` shifts long names one tile left with a table offset of `0xFFFE` loaded by `ldos` (zero-extended), so the plate is written at `0x01011442` and only reaches tile RAM through the mirror. Metal Sonic's plate uses the same offset.
- **A board timer that is not counting reads `0xFFFFF`, not 0** (`IRQT_IDLE`; MAME `machine_reset` / `model2_timer_cb`): before its first write and after it expires. `mem_init` resets the timers, so every boot starts so. STF's `rand` (`0x66B0`) adds all four timers into its state at `0x500098`, and STF never arms timer 2, so from character select on every random number (the CPU opponent's choices included) took a 0 the board does not give. Attract never reads an idle timer, so attract and the replay fight are unchanged.
- **Sega Rally's wheel is a 315-5649 I/O board, and its analog port is a mux that moves on by itself** (`io_5649.h`, `quirks.io_5649`; MAME `model2.cpp` srallyc). Register k is byte `(k/2)*4 + (k&1)*2` of `0x01C00000` (umask `0x00ff00ff`). Port B (`+0x02`) is IN0, C (`+0x04`) the gear lever (bits 4-6, active high, the rest read 1), D (`+0x06`) the hand brake, G (`+0x0C`) the DIPs. `+0x1E` is the ADC: a write picks the channel, and every read answers it and moves on to the next (0 steer, 1 accel, 2 brake). The game reads three a frame, so the channel it starts on walks 0, 3, 6, ... and a model that does not move on reads the steering for the pedals. The wheel's centre and travel follow the operator manual's test-menu spec (HANDLE centre 7D-83, full left < 2D, full right > D3; pedals < 30 off, > C0 on): default centre 0x80, ±0x58 (0x28..0xD8), 10 steps a frame. `--wheel-range` / `--wheel-speed` / `--wheel-center` adjust it on this machine only: the wheel moves on the vblank count, its state is savestated (`IO5649`), and a board on netplay inputs takes the defaults, so two machines read the same value.
  - **Port A bit 0 switches IN0's top half** (MAME `in0_r`): while it is up, bits 7, 6 and 4 read 1 and bit 5 is the EEPROM's DO (`eeprom_in0`, below). Sega Rally clocks its EEPROM with the bit up every frame. *Symptom:* START (IN0 bit 6) took the game to its TEST MENU instead of car select.
- **Every board has a 93C46 serial EEPROM on the I/O chip's port A** (`eeprom_93c46.h`; MAME `eeprom_w` / `in0_r`, `eeprom_serial_93cxx`; Pinboard #965): bit 5 DI, bit 6 CS, bit 7 CLK, written in that order; bit 0 switches IN0 to control mode, where it reads `0xC0 | DO << 5 | 0x10 | IN0 & 0x0F`. 64 words, erased (`0xFFFF`) and locked by `mem_init`, so every install and netplay reset starts from the same chip. Port A is `0x01C00000` on the 315-5649 boards (`io_5649.h`) and offset 0 of the I/O buffer on the others (`input_io_write_cb`).
  - **DO is READY between commands, and a write cycle ends on board time** (`vbl_count * IRQT_CPU_HZ + vbl_phase`; MAME's 1.75 ms write, 1 ms erase, 8 ms for the whole chip), so every machine sees it go high at the same instruction. Sega Rally (`0x1DE0`) and Virtual-On (`0x280C`) poll it after their writes; the poll changes what the i960 runs (`NETPLAY_PROTO_REV` 24).
  - *Symptom that surfaced this in Dynamite Cop:* it keeps its settings in an `S32A` block there, which it writes itself when the chip reads erased. With DO always 1 it read all-ones settings: two credit counters on screen, and a demo whose player died at once.
  - The words are in savestates and rollback (`EEPROM`) but not on disk yet: every boot starts erased, and Dynamite Cop writes its defaults again.
- **Dynamite Cop's 315-5881 security chip deciphers what the game puts in its RAM** (`crypt_5881.h`, a port of MAME's `sega_315_5881_crypt_device` and `model2_5881_mem`, key `0x2c2a4a93`; Pinboard #965). The game writes the enciphered words at `0x01D80000`, sets an address and subkey at `0x01D90000`, and reads the plain words out of `+0xE` (the first read after an address write is a dummy 0). The port matches MAME word for word on both of the game's requests.
- **The words at `0xE00000` are the i960's wait states, one per memory area, written by the game at boot** (Pinboard #762, #763), not the sound 68000's (sound-board.md). MAME and the cycle table ignore them; the board timing model reads them (i960.md).
- **`GEO_CAPTURE_SIZE` ≥ 32768.** Smaller sizes wrap mid-frame and produce partial 3D snapshots / flicker.
- **`mem_init` clears the four heap regions in place on a re-init; it never frees them** (`mem_region_fresh`). `main_data`, `xtra_data`, `texram0` and `texram1` keep their addresses for the life of the process. A netplay session re-runs `mem_init` on the emu thread while other threads hold those pointers, and none of them take the emu mutex for the whole of their read: the frame callback loads `texram0` once and decodes two million texels through it (`game_render_upload_atlas`). Do not go back to `free` + `calloc`, and do not try to fix the readers one at a time instead — `1c62bf0` did that for the MCP bridge and the crash simply moved. `tests/mem_test.c` holds the addresses across a re-init.
  - *Symptom that surfaced this in STF:* accepting a netplay challenge killed any client that had a window, every time, between "barrier released … resetting the board" and the first frame. Headless clients have no frame callback and never saw it, so the graders and the bot's training runs were all green. It faults rather than reading stale bytes because a 1 MB block is its own mapping and `free()` hands the pages straight back.
  - *How it was found, which is worth repeating:* Windows had already kept a dump (`%LOCALAPPDATA%\CrashDumps`, LocalDumps is on for this machine) and `cdb` is installed with the Windows Kit. The release build has no PDB, and did not need one: the faulting instruction was a bounds-checked, in-range read through a heap pointer, the pointer in the register was not either of the bus's current `texram` pointers, and the netplay log ring in the dump said the reset had just run. The WER record's PE timestamp (`P3`) says which exe a fault offset belongs to.
- **`0x98000C` reads a frame-number bit over the low two bits written** (`irqt_videoctl`; MAME `videoctl_r`, on every Model 2 board): bit 2 is frame bit 1 in 30 Hz mode (`0x10000000` bit 2 clear), frame bit 0 at 60 Hz. The 2A map (`model2a.h`) and the 2B SHARC COP (`model2b_cop.h`) serve it; STF's map leaves it plain storage, which STF never reads.
- **Virtual-On needs a comm board that is there, with nobody on the link** (`m2comm.h`; MAME `m2comm.cpp`, `M2COMM_SIMULATION`, one cabinet). Shared RAM is `0x01A00000-0x01A03FFF`, mirrored at `+0x10000`; CN at `0x01A04000` reads `0xFE | cn`, and a write of 1 zeroes the RAM, sets `[1] = 2`, the frame size `[0x12..0x13] = 0x0E00` and the offset `[0x14..0x15] = 0x1C0`. FG at `0x01A04002` reads `0x7E | fg | (zfg ? 0 : 0x80)`. Each vblank while CN is 1 the board's Z80 toggles zfg and writes "no link yet" (`[0] = 0`, `[2] = [3] = 0xFF`). Here that runs lazily: an access first catches up on the vblanks counted since the last one (`g_irqt.vbl_count`).
  - *Symptom:* with COMM reading as no board, VON's vblank handler (`0x1438`) set link state `0x5024F4` to `0xFF` and the machine select (state 4, substate 0 at `0x18C00`) waited on it forever: a black screen after the coin. With the board there the link state is `0xFE`, standalone, as in MAME.
  - `memory.h`'s COMM stub (`0xFE` at even bytes) stays the default: another game only asks whether the board is there. A profile opts into `m2comm_install` and saves `g_m2comm` as a savestate extra.
  - **The link** (#959, MAME's `comm_tick` for two nodes): `m2comm_set_peer` gives the board a datagram send/recv pair; `g_m2comm_link` holds the ring and is not saved. With no peer nothing changes. With one, the master (`[1] == 1`, which the ROM writes from its role) waits `0xE8` passes, sends the token `{FF,1,0}`, the slave counts itself in, and the master sends the size `{FE,2,2}`: ring up is `[0] = 1`, `[2]` = node id, `[3]` = 2. Then each pass the master sends `{id, window}`, the slave answers each frame it takes, and a taken frame lands at `0x2000 + [0x14..15]` and toggles zfg. The window is `[0x14..15]` bytes from `0x2000` (vonj halves `0x0E00` to `0x700` itself), not MAME's whole `0x0E00`.
  - **One data frame per pass, in order, never coalesced.** Virtual-On signals handshake steps (the stage, state `0x24` at `+4`) as one-frame values; a board that takes the newest of several drops them. The master repeats the token and the size every 60 quiet passes, as datagrams get lost. No `0xFC` vsync frames, no relay, two nodes.
  - **The shared RAM is RAM, not a FIFO** (no `no_burst`): the ROM copies its 0x700-byte packet with `ldq`/`stq` (memcpy `0xF5D40`), and with `no_burst` all four words of a quad went to one address, so only every fourth word landed and every packet failed its `+0x556` check.
- **Virtual-On's attract runs 12 frames behind MAME's, and that is the 60 Hz vblank, not the COP** (Pinboard #955). Its loads are pure i960 work: the texture loader at `0x27E50` ("Load Texture", bank 0 from `0x28168`, bank 1 from `0x281BC`; again at the attract's first scene) runs with no interrupt. Our frame is 416,667 cycles against MAME's 434,600 (57.52 Hz, `irq_timer.h`), so each load takes 4.3% more frames: banks 0 and 1 take 119 frames each against 114, and the attract load 124 against 118. The cycle table is MAME's: costing a MAME trace of one loader frame with `i960_cycle_cost` gives exactly 434,600. Against a blank MAME nvram the offset is +6 after boot and +12 from frame 1169 to the tutorial (events at MAME 3910/4120/4210, ours 3922/4133/4223). After boot, the game's vblank counter (`0x5024E4`) keeps the same offset.
  - The EEPROM pulls the other way. With a blank EEPROM, MAME's game writes its defaults and polls the busy bit (bit 5 of `0x01C00002`, loop at `0x2800`) for ~7 frames. Our port reads that bit as 1 (no EEPROM), so ours waits ~2. Against a MAME with a saved EEPROM there is no wait, and the offset is ~6 frames larger.
