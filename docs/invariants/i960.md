# i960 CPU (board-level — every Model 2 game)

Part of m2-hle2's load-bearing invariants, indexed in [CLAUDE.md](../../CLAUDE.md): facts reverse-engineered or debugged into the emulator, in no datasheet. Do not re-derive them.

- **`chkbit` sets `CC_NO` (0x0) when the tested bit is 0**, not `CC_NE` (0x5). `bno` depends on this; getting it wrong inverts all `chkbit`+`bno` / `chkbit`+`bo` branch logic.
  - *Symptom that surfaced this in STF:* Espio's tongue drew every frame in the Rocket Metal attract cutscene because `bno rd_te_pass` never branched. Since this is i960-core behaviour, the same bug would surface in any Model 2 game that uses `chkbit`+`bno` — which is most of them.
- **`cmpobX` / `cmpibX` always update the condition code**, even when the branch is not taken. Downstream `bg` / `bl` / `be` read those CCs.
- **MEM mode 0x5 is IP-relative**: `effective = IP + 8 + disp`, where `+8` is relative to the *start* of the 2-word MEM instruction, not the next.
- **FP-from-GPR is bit-reinterpret, not int→float convert** — `memcpy` semantics.
- **`call` / `ret` frame layout**: the new frame is `(sp + 63) & ~63`, and that is `g15` (FP); SP starts 64 above it (MAME `do_call`). Zero the new locals; `pfp` is the caller's FP, as on the hardware (Pinboard #965; it was 0). `ret` restores all locals and the caller's `g15` (`frame_fp[]`).
  - *Symptom that surfaced this (m2-pacman issue #1):* `g15` used to be set to `pfp`, which this model then left at 0, and SP to the frame base. STF's compiler never addresses through FP, so nothing showed. gcc960 code keeps its locals at `fp+N`: the homebrew's `main` counted its loops in ROM and never left its boot loop.
- **The processor starts on the PRCB's interrupt stack, at PC `0x001F2002`** (priority 31, interrupted state, supervisor; MAME `device_reset`): FP = PRCB+0x18, SP = FP+64 (`sfight_install`). An IAC re-initialise moves neither. m2-sdk's kernel enters `main` with `b` and never leaves the interrupted state, so its interrupts nest on the stack it is on.
- **`flushreg` puts the cached frames in memory, and a `ret` below what it flushed reads its frame back from there** (`i960_flushreg`, `i960_ret_mem`; MAME `flushreg`, `do_ret_0`; Pinboard #965). The model keeps a frame's return IP in the callee's set; memory gets the hardware's layout, the IP in the caller's r2, at the FP rounded down to 64. The returning `ret` takes FP from `pfp`, the locals from there and the IP from their r2. If `pfp` is not the top cached frame's FP, the program rewrote the chain (a task switch): every cached frame is in memory already and the cache empties. `hle_call` keeps the FP in `pfp` so a flushed `ret` finds a hook's frame.
  - *Symptom that surfaced this in Dynamite Cop:* its tasks switch by `setjmp` / `longjmp` (`0x2E60` / `0x2E80`): `flushreg`, a `pfp` written by hand, `ret`. The cached `ret` went back into the task that switched out, and attract hung in state 9.
  - *And in Sega Rally:* the boot calls `0x5C0`, which flushes, sets return status 7 and returns through memory to `0x590`. With FP at 0 (its install did not start on the interrupt stack) the caller's frame went to ROM and the board stopped at IP `0x10`; `srallyc_install` now starts FP on the PRCB's interrupt stack like the others.
- **`modpc src, mask, src/dst`: the mask is src2, the new bits come from src/dst, which then gets the old PC** (MAME `i960.cpp`). It used to take the mask from src1 and the bits from src2, so the boot code's `modpc r4, r4, r5` (drop the priority to 0) raised it to 31.
- **An interrupt pin's vector is byte `pin` of the interrupt control register** (the program's `synmov` to `0xFF000004`, which lands in the IAC block), **and its handler is word 9 + (vector − 8) of the PRCB's interrupt table** (`hle_irq_vector_handler`). STF's table names exactly its profile's `irq_handler` (vectors 12–15: `0xC40`, `0xD10`, `0xD30`, `0xDF0`). A profile with `irq_vectors` takes a pin it names no handler for this way, on the interrupt stack with MAME's padding frame and the vector's priority (`hle_interrupt_on_stack`). STF's handlers still run on the interrupted SP (`hle_interrupt`), as they always have; a gcc960 handler that stores `g0`–`g15` from its SP broke m2-pacman's picture that way.
  - **The interrupt table and the interrupt stack are the ones the processor took with the PRCB, not what the PRCB holds now** (`i960_prcb_cache`, `cpu->intr_table` / `intr_stack`). The IAC reinitialize reads them; a profile that starts on a PRCB in ROM has them read at the first interrupt (`i960_prcb_take`), which gives the same words. MAME reads the PRCB again at every interrupt, and so patches Pilot Kids and Zero Gunner, which clear their RAM PRCB after the reinitialize.
    - *Symptom (Pinboard #1538):* Pilot Kids copies its PRCB to 0x500000, reinitializes on it, then clears 0x500000–0x54FFFF (loop at 0x72C). Its first vblank read a table at 0, ran wild, and read the 315-5881's port with a garbage header, whose decompressor wrote past its line buffer (`c5881_line_fill`, now bounded to the line) until the process crashed.
  - **A profile that names no `irq_handler` and no `irq_vectors` gets no interrupts at all**, silently (`emu_irq_handler` answers 0). A game that waits for its frame by polling still boots and draws. Use `irq_vectors` for a new game.
    - *Symptom that surfaced this in Sega Rally (Pinboard #620):* scenery and the title logo came out black and the cars were fine. The vblank handler (0x5A0490) clears the texture-upload budget flag at 0x202004 and arms timer 2, whose interrupt sets it again; the upload queue (0x5A2A50) copies only while it is 0. With no interrupts, the flag stayed at its boot value of 1 and the course textures never left data ROM.
- **Register-pair (`reg_quad`) ops are big-endian** even though the CPU is little-endian overall.
- **The four "not" logicals invert different operands**: `andnot` = src2 & ~src1, `notand` = src1 & ~src2, `ornot` = src2 | ~src1, `notor` = src1 | ~src2 (MAME `i960.cpp`). `notand` used to be a copy of `andnot`.
  - *Symptom that surfaced this in STF:* the top quarter of both texture sheets was never written. `sub_4C444` clears bit 0 of each mip destination with `notand g6, 1, g6`, so every mip level went to the wrong address. Once fixed, `tools/grade-texram.mjs` shows both sheets byte-identical to the explorer.
- **`movl` / `movt` / `movq` honour the literal flag: a literal source fills every destination register** (MAME `i960.cpp`). They used to read registers regardless, so `movq 0, r4` copied pfp/sp/rip/r3 into r4–r7.
  - *Symptom that surfaced this in STF:* a few thousand frames into a fight the game stopped itself on its "max poly / err poly" screen. `adv_set_action` "clears" each fighter's damage and crush-stage arrays with `movq 0, r4` + `stq`, so the stages held a return address (0xBD80). `damage_unit` indexed the empty crush table with it, ran the Fighting Vipers armour-break effect, and `efc_crush_parts_set` wrote model numbers like 0x3000 over the forearms and shins; `set_obj` rejected them.
- **An interrupt is not a call: `ret` from a handler restores AC and PC.** Deliver interrupts with `hle_interrupt`, never `hle_call`. Otherwise a handler's compares leak into the condition code of the instruction it interrupted.
  - *Symptom that surfaced this in STF:* attract crashed about 45 s in. A timer interrupt landed between `cmpo r14, 0x10` and `bg` in `unpack_lod_data`'s bit-buffer refill, the Huffman decode lost sync, and its output overran into the code tree. It only showed once the `notand` fix changed attract timing; the bug predates that fix.
- **`concmpo` / `concmpi` compare only when condition-code bit 2 (less, `0b100`) is clear**, and then set E (`src1 <= src2`) or G. Otherwise they leave the code alone. `cmpi x, lo` + `concmpi x, hi` + `be` is the ROM's range test `lo <= x <= hi`. They used to test the equal bit instead.
  - *Symptom that surfaced this in STF:* in the attract fight, Bean won the mutual grab that Sonic wins on the board. `get_en_info` range-tests the facing angle against ±0x1554 this way to build the enemy-info flags at `rob+0x720`, which the throw logic reads, so the flags were wrong from the first frame of the fight. `tools/match-replay.mjs` found it (see tools/README.md, "match_replay").
- **`cmpr` / `cmprl` set 000 for an unordered compare (a NaN)**, not G (MAME `cmp_d`). `bge` and `ble` then do not branch. It used to fall through to G, so `coli_recalc_pos`'s `cmpr r15, r8; bge` (`0x2DA8C`) took a NaN limit as a pass. Since the `Fn_area_coli` fix below, attract no longer hands it one; `tests/i960_test.c` holds it.
- **Sega Rally runs the i960 on a board timing model; STF and FV keep MAME's table** (`game_quirks_t.i960_board_timing`, `src/board/i960_timing.h`; Pinboard #667, #744, issue #305). The model's shape is the 80960KB manuals': a 512-byte direct-mapped instruction cache of 16-byte lines, a load scoreboard that stalls only an instruction reading a register a load is still filling, posted stores. Its numbers are the owner's board benches (#611-#738): a line miss, a branch into a missed line and the word it lands on, a hit on a new line (hidden behind a long instruction), each load and store by region and width, a scaled index, the taken branch, mulo. Each cost is fitted on the bench that measures it alone, then every bench is held to the model: all but six are within their noise (#744's residual table). Do not tune it to a game's picture. Sega Rally budgets its car LODs by timer 3 (`0x5BADE0` -> `0x20AAC0`, quota row picked at `0x5BB2A0`): at the table the frame ends early, the row is 8, and the third car ahead of the player goes to physics on the grid and lags the pack at GO, as in MAME. On the model the race holds row 7 and the grid 5-7 (the PS2 port's `FUN_0012bf70` always takes row 7; the old flat 2.3x gave 5-7). The costs are STF's wait table's: each game writes its own at `0xE00000` (one word per area, 1/2/4/8/0x10 = 0-4 waits, 0x20 External, +0x40 DRAM; Pinboard #762), and `i960_bt_areas` moves every access and line fill a cycle a word for each wait its area differs from where the cost was measured (Pinboard #763). Sega Rally's program ROM and backup SRAM are 4 waits (STF 2, and work RAM's 1 stood in for the SRAM), its code in work RAM 1. Last Bronx, Zero Gunner, Gunblade and others also have a 4-wait ROM, Power Sled 3. MAME stores the table and ignores it. Measured on the board (`stf-wait-bench`, Pinboard #766, read in #772): a wait is a cycle a word for `ld`, `st`, `ldq` and `stq` alike, in program ROM (2-4 waits) and work RAM (1-3); code fills a line at its own area's waits wherever it is (download RAM at 1 wait runs as program ROM extrapolated to 1, at 3 as program ROM's 3); a branch into a missed line pays **6** cycles a wait, not 4 (`I960_BT_BRWAIT`, the next line's prefetch already on the bus); and **the DRAM bit is not free**: work RAM against download RAM at the same waits is 0.84 a load (1.11 at 3 waits), 0.47 a store (1.09), 1.19 a quad and 1.20 a line fill, about a cycle a burst (`g_i960_bt_dram_ld`/`_st`, `I960_BT_FILL_DRAM`). So a 2A's RAM at 0x200000 and the backup SRAM (no DRAM bit) take work RAM's cost less the bit at their own waits, and code in work RAM fills 2.8 cycles sooner than program ROM's, not 4. Download RAM is a little sub-linear between 1 and 3 waits (at 1 a load is 0.25 and a store 0.5 dearer than a straight line through 3 says); the model uses the 1-wait bench, which is Sega Rally's setting. Work RAM at 3 waits + DRAM never read back the bench's code (every packet 0); no game uses it. Assumed still: a 2A's regions cost what the 2B's at the same addresses do. Sega Rally keeps much of its race state in download RAM and backup SRAM, and with them in the 45-cycle I/O bucket the race ran at row 0. With the measured costs the race still holds row 7 (timer-3 budget +0.6%). The model's state (cache tags, scoreboard, `g_i960_cyc_frac`) is board state, saved by srallyc; m2_spin and m2_texload decline while it is on. `--i960-timing table|board` (main and det_digest) overrides the profile.
- **`shrdi` is a dividing shift: arithmetic right, rounded toward zero** (MAME `i960.cpp`), so -15 >> 1 is -7. It used to shift the 64-bit pair dst:src2, taking the destination's old bits.
  - *Symptom that surfaced this in Sega Rally (Pinboard #642):* the cars clipped into the road and sat tilted on the grid. `0x5DA128` halves (pedal byte - 0x30) with it, -16 came out as 0x7FFFFFF8, and the 9.4e7 that followed reached TGP `0x21004242`'s fifth argument. STF uses it too: `energy_disp` (`0x7A774`) eases the energy bar by half the gap, and `_ScrollColor_Initialize` (`0x2E640`, `0x2E70C`).
- **`ret` with return status 7 in supervisor mode is an interrupt return** (MAME `do_ret`): the PC and AC saved under the frame come back, PC from FP-16 and AC from FP-12, after the frame is popped. Virtual-On's boot code (`0xA30`) leaves priority 31 this way. It used to be a plain return, so the CPU stayed at priority 31 and no interrupt was ever taken: no vblank, no coin. STF and FV never return with status 7 (their digests are unchanged). `i960_test` holds it.
- **`movre` (`0x6E1`, the undocumented encoding Dead or Alive also uses, and `0x6E9`) moves an 80-bit extended real** between three registers (the first a multiple of 4; the third's low half is the sign and exponent, its high half ignored) and an FP register or literal. The FP registers are doubles here, so the move converts (`i960_double_to_ext` / `i960_ext_to_double`: integer bit work, round to nearest even, denormals, infinities and NaNs kept). Virtual-On saves and restores fp0-fp3 with it in its interrupt entry and exit; it was an unimplemented opcode that halted the board on the first interrupt.
