# Several boards in one window (`core/emu_multi.h`, `ui/multi_view.h`, Pinboard #1910)

Experimental, desktop only. `m2hle --boards N --rom <zip> --run` (N = 2..8, or `all`) runs N cabinets of the set in one process and shows them side by side (`multi_view__place`): a ring whose MASTER plays itself (`ring_op`, Power Sled's Main) has it centred above one row of its slaves, any other ring is one row (Daytona, Virtual-On), unlinked boards a grid. A click on a board, or Ctrl+1..8, gives it the focus. **Emulation > Boards** picks the same from the window: One board, or 2 up to the game's most (`multi_view_menu`). A new count starts every board from power-on; One board loads the set again, as it starts alone (so Power Sled's ride gets its hidden Main back, SOLO).

- **The boards take turns in the one set of globals**, as GGPO's twin does (`core/emu_twin.h`, [ggpo.md](ggpo.md)): each one waits in a rollback snapshot of its own (`rollback_save_to` / the part copies), with its `g_m2comm_link` swapped beside it (the link is outside savestates). A round copies each board in and out once (2 x N x ~7 MB). No `savestate_bus_changed` on a swap: the regions are the same, only their bytes change.
- **The UI thread runs the rounds, not the emu thread**: a board's picture is drawn while that board is in the bus, and the GPU is the UI thread's. While multi is on `emu_run_running` only naps. `multi_view_frame` paces the rounds by the host clock (one per `EMU_SLICE_US`, at most 4 owed), emu mutex held. A round starts with the live board and ends with the board in focus live, so the keyboard, the sound, the debugger windows and the bridge all see the focused board. The other boards are muted.
- **Each board's picture has its own render state**: a `video_state_t` (the composed-layer gens are per vid; the bus gens are monotonic and shared), a `geo3d_state_t` (a copy of the main one's settings), a render bank (`game_render_use_bank`: atlas, luma and colour-table images and the CPU atlas copy, with their upload gens) and an offscreen target. The bus's `tex_dirty` flags are shared: each board is drawn right after its own frame and that draw consumes them. A bank that is not valid yet decodes the whole atlas and clears the flags (`game_frame__upload`). Colour ramps and shade rows are off while multi runs (they are built from one board's tables), and so is the sub-frame lerp.
- **Linked games are a ring, as MAME's m2comm is.** The ring-up token 0xFF is counted up by each slave. The master's 0xFE {count, count} goes around, and each slave takes `id = msg[1]` and passes it on minus one, so on Daytona the slaves get ids 8, 7, ..., 2. Data frames carry the whole `frameSize` (`m2comm_set_mame_frames`, `m2comm__payload`), copied to 0x2000 + frameOffset. Our two-node datagram link sends only the window, so it stays as it was, and `mame_frames` is false outside multi. Board b sends to board (b+1) % N into a pending queue, and the queues are committed at the end of the round. So what a board sends in round R the next one reads in round R+1, and the order the boards run in never shows.
- **Roles come from a cold boot, as a room's do.** Board 0 boots alone, muted, until the profile's `ring_role` (else `link_role`) can write MASTER into its backup block (at most `EMU_MULTI_BOOT_MAX` frames). That block is board 0's, and SLAVE's is everyone else's. Every board then boots from power-on with its block. Daytona has `ring_role`, not `link_role`: `daytona_settings_role` writes LINK ID (settings +0x0B: 0 single, 1 master, 2 slave) and the settings CRC. A `link_role` would turn Daytona netplay into a linked session (`netplay.h`, `linked = link_role`), so it stays unset. daytona93 has no settings header to match, so it boots unlinked.
- **A linked game's ring has its cabinet count** (`link_cabinets`, `emu_multi_count`): `--boards` above it is held to it, and `all` is it. Daytona has 8 (the "8人まで対戦できます" link screen). Power Sled has 5: a Main and four rides. Its Main's NETWORK screen lists MAIN, RELAY and the SILVER, RED, BLACK and YELLOW rides, and two rides of one colour are an ERROR ("change RIDE ID (color)"). The default profile has no Relay unit (only RELAY: NG, which the race tolerates); "Power Sled - Arcade" adds one. Unset is 2: Virtual-On's one-on-one, and Motor Raid, whose cabinets would each need their own CABINET ID. An unlinked game takes any N (`all`: 2).
- **A board can run a set of its own** (Pinboard #1918): `--board-rom N=<zip>` (N from 1), or a profile's `ring_sets`, the site's set per board (used when every one of them is beside the loaded zip, and then `ring_sets_n` is the ring's count). `emu_multi__load_sets` loads each other zip once (`g_multi_load_set`, main.c's `multi_load_set`: the profile by basename, its parent) and refuses the lot unless the board type and every region but the program and the sound board match the loaded set. Board 0 keeps copies of the loaded program and sound program. A turn copies the board's program into `bus->rom`, its 68000 program into `g_sound.rom` and points `g_sound.samples` at its samples (`emu_multi__use_prog` / `__use_sound`), and `g_active_profile` is the board's, so its savestate extras (registered under its own id, `savestate_extra_mine`) come and go with it. When multi stops the set left in the bus is put back to the loaded one (`emu_multi_sets_restore`). Daytona with `--board-rom 2=daytonat.zip` (program only) links as three.
- **Power Sled has two profiles for the set.** `powsled` (the default) is the ring of five above, its Main the Slave program patched (`powsled_set_unit`). "Power Sled - Arcade" (`powsled_arcade`, `--profile powsled_arcade` or the Game menu) runs the whole site when `powsledm.zip` and `powsledr.zip` are beside `powsled.zip`: the Main runs powsledm (MAME's Relay dump with `init_powsledm`'s three bytes, applied at load), four rides the Slave program, and a sixth board the Relay, powsledr. The Relay build runs as its bytes say (no unit patch, no settings seed). It clears 0x01D80000.. at boot, which neither MAME's Power Sled map nor ours has (unmapped WARNs, harmless). Without the two zips Arcade is the ring of five. The Relay is drawn centred in a row of its own below the rides (`emu_multi_last_below`). The labels, the layout and the Boards menu read the ring's profile (`emu_multi_ring_profile`), not `g_active_profile`, which is the focused board's own (powsledm, powsledr).
- **Slaves that must differ get a seat** (`ring_seat`, written into the slave's backup block after the copy): Power Sled's ride colour, byte 8 of all three settings copies at 0x000/0x100/0x200 (no checksum; two copies that agree win).
- **Every pad and wheel plays a board of its own** (`ui/multi_pads.h`, Pinboard #1914): while multi runs `pad_refresh` reads each device alone (`g_pad_multi`, `pad_multi_read`: its held bits and its wheel and pedals) and presses none of the shared actions, so `g_input.held` is the keyboard's alone. The keyboard plays the board in focus. `multi_pads_frame` gives each device's bits to its board (`g_multi.pad_held[b]`, `pad_an[b]`), and the round puts them in `g_input.held` and `g_io5649_host` for that board's frame (keys too on the focused one, `use_net` off, so the analog wheel works on every board) and back after it. A device's seat is Auto, a board or None (**Emulation > Boards > Controllers...**, the Board controllers window); Auto devices take the boards nobody chose, in order, wheels then gamepads as SDL lists them, skipping a Main with an operator. Seats are for the run, by SDL id. The Controls window's gamepad pick does not apply while multi runs (every pad plays); its device kind does. A held pad button frames its board green. Force feedback still follows the focused board only.
- **A Main nobody plays is worked by the profile's operator** (`ring_op`, else `link_solo`), from every player's buttons (the keys and every board's pads). Focus starts on board 2, the first ride. Power Sled's `powsled_ring_op` is SOLO's `powsled_solo_op` with one gate: between races (race state 4) it opens entry only once a rider has pressed Entry, so until then every ride plays its attract (SOLO opens entry at once). Z (Entry) calls a race, Z again enters, and the Main closes entry and starts the race for every ride.
- **The labels say what each cabinet is** (`ring_names`): Power Sled's Main is the site's big screen over the line of rides (the LIVE camera) and the operator's panel, and each SLAVE a ride, by colour. Without a list: MASTER / SLAVE.
- **The battery is detached for the run** (`backup_ram_detach` / `_reattach`): the roles go into backup RAM, and the player's own file must not end up with a SLAVE's block. A new set, or quitting, stops multi first (`load_active_profile`, `cleanup`).
- **Not part of the board.** With `--boards` off nothing here runs: `mame_frames` is false and the only change to the frame upload is where its statics live. `--headless` refuses `--boards` (no window, nothing to draw into). GGPO, replays and the follow feed are stopped when multi starts.
- Daytona x8 on the container's Xvfb (llvmpipe): the ring is up with ids 1..8 and nothing dropped, and the attract shows the "8 players" link screen. It runs at ~15 rounds a second, most of that drawing 8 pictures in software. Power Sled x5: four sleds race (positions 1-4) and the Main shows the LIVE camera. Virtual-On x2 links. STF x2 runs unlinked (it has no comm board).
